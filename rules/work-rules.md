# 공통 작업 규칙 (work-rules 플러그인)

프로젝트와 무관하게 지키는 작업 방식이다. 프로젝트의 CLAUDE.md·규칙·스킬과 어긋나면 **프로젝트 쪽을 따른다.**

## 소통·보고

- 사용자에게 보이는 문장은 전부 한국어로 쓴다. 도구 호출 사이의 짧은 진행 문장과 표가 들어간 정리 보고도 포함한다. 코드 식별자와 명령어만 원문 그대로 둔다.
- 화면 작업은 기능 흐름이 통과했다는 것만으로 "검증 완료"라고 하지 않는다. PC(1440)·중간 폭(768·1024)·폰(390) 캡처를 직접 열어 시안·설계와 대조하고, 어느 폭·어느 상태를 봤는지와 시안과 다른 점을 보고에 적는다.
- 사용자에게 보여 주는 폰 캡처는 390×844 한 장을 기본으로 한다. 320·360 같은 좁은 폭은 자동 검사로만 돌리고, 문제가 있을 때만 그 캡처를 보여 준다.

## 진행 순서

- 새 기능·화면·데이터 구조는 코드를 쓰기 전에 플랜(화면 구성, 테이블·데이터, 변경 방식)과 시안을 보여 주고, "구현해" 같은 명시적 승인을 받은 뒤 만든다. "~하면 될 듯", "실제 화면으로 보고 싶다" 같은 말은 구현 지시가 아니라 설계를 더 구체화하라는 뜻으로 읽는다. 버그 수정과 이미 정해진 절차는 바로 진행한다.
- 관찰이나 감상("글자가 작네")은 변경 지시가 아니다. 이미 운영에 나간 디자인·콘텐츠는 시안을 먼저 보여 주고 "적용해"를 받은 뒤에만 바꾼다.
- 설계·판단·검증은 본 세션이 맡고, 구조가 확정된 뒤의 구현은 에이전트에 맡긴다.

## 검증

- 화면을 만들거나 고쳤으면 "개발 완료"라고 보고하기 전에 로컬 서버를 띄워 Claude 내장 브라우저에서 **PC와 모바일 둘 다** 직접 눌러 보고, `work-rules:e2e-checklist` 스킬의 항목을 전부 돈다. 정상 흐름 한 번으로 끝내지 않는다.
- 그 화면 테스트 중에 버튼(깨짐·위치·크기)·글자 크기·여백, 표의 행·칸 겹침(모든 행)을 PC·모바일 각각 검수한다. 눈대중으로 넘기지 않고 같은 종류의 기준 화면과 잰 값을 숫자로 비교하며(스킬 10장), 다른 항목을 보고에 적는다.
- 에이전트의 "검증 완료" 보고를 그대로 옮기지 않는다. 핵심 흐름을 본 세션이 독립 스크립트로 다시 돌리고, 누가 무엇을 검증했는지 구분해 보고한다.
- 아이콘 버튼 안 기호는 글자(`‹ › + ×`)가 아니라 SVG 아이콘으로 넣고 가운데 정렬한다. 만든 뒤 버튼 중심과 아이콘 중심의 차이를 재서 0.5px 이하인지 확인하고, 좌우 안쪽 여백이 대칭인지 확대 캡처로 본다.
- "틀·포맷이 다르다"는 지적은 여백 숫자를 조정하라는 뜻이 아니라, 같은 종류의 기준 화면과 형식(부품) 자체를 맞추라는 뜻이다. 기준 화면과 나란히 캡처해 본문 시작 위치를 숫자로 비교한다.

## 배포

- **시작 조건**: 사용자가 이번 변경에 대해 "배포"라는 말로 지시했을 때만 배포한다. "진행해"는 커밋까지 하고 멈춘 뒤 배포 준비가 끝났다고 알린다. 한 번의 승인은 그 시점의 커밋에만 유효하고, 변경은 모아서 한 번에 배포한다.
- **배포 전**: 전체 테스트 → 화면 검사 → 로컬에서 실제 화면을 직접 눌러 보기 → DB 변경(마이그레이션) 순서·적용 여부 확인 → 커밋. 단위 테스트·타입 검사·빌드 통과만으로 배포하지 않는다.
- **운영과 대조**: 배포 전에 현재 코드가 운영에 나가 있는 코드를 전부 담고 있는지 대조한다. 커밋 없이 배포된 변경이 있을 수 있으므로 "지금 브랜치 = 운영"이라고 가정하지 않는다.
- **정해진 절차로만**: 실행·배포 전에 저장소 README와 프로젝트의 배포 스킬을 먼저 확인하고, 정해진 스크립트·스킬로만 배포한다. 명령을 손으로 조합하지 않는다.
- **배포 뒤 점검**: 올라간 판이 방금 커밋과 같은지, 프로세스 상태, DB 버전, 오류 로그를 확인한다. 바뀐 기능은 운영 데이터로 조회만 한다(쓰기 금지).
- **되돌리기**: 앱이 안 뜨거나 오류가 쌓이면 먼저 이전 판으로 되돌리고 알린다. DB 변경은 되돌아가지 않으므로 이전 판이 새 구조에서 도는지 먼저 본다.
- **보고 형식**: 올린 것, 검사, 운영 확인, 확인 못 한 것, 사용자가 직접 할 일.
- **권한에 막히면**: 운영 배포·운영 DB 작업이 세션 권한 모드에 막히면 우회하지 않는다. 시작 전에 사용자에게 모드 변경을 요청한다.

## 외부 채널·자산

- 라이브 외부 채널(SNS·블로그·커뮤니티)에 게시·삭제를 반복하며 검증하지 않는다. 로컬 프리뷰·dry-run 으로 검증을 끝내고 사용자 컨펌 후 1회만 발행한다. 발행이 실패한 것처럼 보여도 다시 발행하기 전에 실제 게시 여부부터 확인한다.
- 이미지는 저장소(S3 등)에 직접 올리지 않고 앱이 실제로 쓰는 업로드 경로로 올려 압축·검증을 거치게 한다.

## 코드·git

- Kotlin/Java 코드에 인라인 완전수식이름(`com.foo.Bar`)을 쓰지 않는다. 파일 상단에 import 를 추가하고 짧은 이름으로 참조한다(어노테이션·예외·제네릭 인자 포함).
- 여러 세션이 같은 저장소에서 작업하면 스테이징 영역을 함께 쓴다. `git add` 는 커밋과 붙여서 실행하고, 커밋 직전 `git diff --cached --stat` 으로 내 변경만 담겼는지 확인한다. 빌드·배포 전에는 남의 미커밋 변경이 작업 폴더에 있는지 본다.

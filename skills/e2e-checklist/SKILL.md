# 화면 E2E 체크리스트

새 화면·부품을 검증할 때 **정상 흐름 한 번**으로 끝내지 말고 아래를 모두 돈다. 정상 경로 스크립트가 전부 통과해도, 사용자는 값을 이리저리 바꾸며 쓰고 그때 터진다. 구현 에이전트의 보고를 받았어도 본 세션이 이 목록으로 다시 확인한다. 에이전트에 화면 작업을 맡길 때는 프롬프트에 이 체크리스트를 넣는다.

프로젝트에 자체 E2E 체크리스트나 UI 가이드가 있으면 그것도 함께 돈다.

## 1. 방식 — 개발 완료 전에 Claude 내장 브라우저로 PC·모바일 둘 다 직접 눌러 보기

- **언제**: 화면이 바뀐 작업은 "개발 완료"라고 보고하기 전에 한다. 타입 검사·린트·단위 테스트 통과는 화면 테스트를 대신하지 않는다.
- **어떻게**: 프로젝트의 `.claude/launch.json` 에 로컬 서버(백엔드·프론트) 구성을 두고(없으면 만든다) Claude 내장 브라우저로 띄워 실제로 누르고 입력한다. 사용자가 같은 화면을 옆에서 볼 수 있다.
- **PC·모바일 둘 다**: 같은 흐름을 PC 폭(1280~1440)과 모바일 폭(390, 좁은 폭 375)에서 각각 처음부터 끝까지 돈다. 한쪽만 보고 끝내지 않는다. 다크 모드를 쓰는 프로젝트면 다크 모드도 본다.
- **앱이 있는 프로젝트는 네 곳 모두**: 웹 PC · 웹 모바일 · iOS 시뮬레이터 · 안드로이드 에뮬레이터에서 같은 흐름을 돈다. 앱 웹뷰는 브라우저와 키보드·스크롤 동작이 달라 웹 모바일 폭으로 대신할 수 없다. 빠진 곳이 있으면 "확인 완료"라고 하지 않고 보고에 적는다. 앱 시험 빌드는 로컬 개발 서버를 보게 하고(안드로이드는 `adb reverse` 로 localhost 사용), 끝나면 운영 주소로 되돌린다.
- **빠짐없이**: 바뀐 화면의 버튼·창은 하나도 빼지 않고 한 번씩 열어 본다.
- **UI 검수와 함께**: 눌러 보는 동안 10장 UI 검수(버튼 깨짐·위치, 글자 크기, 여백)를 PC·모바일 각각 한다.
- **콘솔 오류 0**: 테스트하는 동안 브라우저 콘솔에 오류가 없어야 한다(15장).
- **단계마다 캡처를 찍어 직접 열어 보고** 겹침·잘림·흔들림·엉뚱한 안내·흐림 상태·버튼 모양을 판단한다.
- 여러 폭 반복(9장)이나 긴 시나리오는 스크립트(Playwright 등)로 돌려도 되지만, 그때도 캡처는 직접 열어 본다.
- 스크립트 PASS(글자·요청값 비교)만 믿지 않는다. 실패했을 때만 캡처를 여는 방식은 금지한다. 요청값은 맞는데 화면에서는 골라지면 안 되는 값이 전부 골라지는 식의 버그는 캡처로만 보인다.

## 2. 값 사이 관계를 거꾸로 바꾸기 (선후 관계)

- 뒤 값을 먼저 정하고 앞 값을 나중에 바꾼다. 예: 종료를 정한 뒤 시작을 종료 뒤로 옮기기, 마감을 정한 뒤 시작일을 앞당기기.
- 그 상태에서 **뒤 칸을 다시 열어 본다.** 못 고르는 값이 열리거나, 휠·목록이 흔들리거나(무한 보정), 전부 흐린 화면이 뜨면 안 된다.

## 3. 수정 화면의 "저장 안 한 값"과 "바로 서버에 저장하는 하위 창"

- 폼 값을 바꾸고 **저장하지 않은 채** 그 화면 안에서 즉시 서버로 가는 기능(하위 항목 만들기, 링크 저장 등)을 써 본다.
- 화면 값과 서버 값이 다를 때 무엇이 기준인지, 오류 문구가 사용자가 모르는 값(DB 에 저장된 옛 값)을 말하지 않는지 본다.

## 4. 기본값 그대로 제출

- 창·폼을 열자마자 아무것도 건드리지 않고 제출한다(자동으로 채워진 날짜·코드·기간이 통과하는지).
- 오늘·지금 경계를 본다: 오늘 00:00 시작, 이미 지난 시각, 마감 당일, 지난 마감을 가진 기존 데이터.

## 5. 오류가 난 뒤

- 오류 → 고침 → 빨간 표시·문구가 사라지는지 본다.
- 문구가 **틀린 칸 가까이** 보이는지 본다. 창 맨 아래에만 뜨면 칸만 빨갛고 이유가 안 보인다.
- 캡처는 칸만 찍지 말고 **창 전체(아래 오류 문구 포함)** 를 본다.

## 6. 실제 사용자 경로

- 새 등록뿐 아니라 **기존 데이터 수정**(오래된 값, 지난 날짜, 지금 규칙에 안 맞는 옛 값), 다른 역할 계정, 폰·PC 둘 다 본다.
- 닫기 방법 전부(바깥 누르기·끌기·뒤로가기·Esc)와 창 위의 창(예: 입력 창 위 달력)을 본다.

## 7. 만들기·고치기 둘 다 (같은 규칙은 같은 결과)

- 입력 창·검사·선택 범위를 바꾸면 **새로 만들기와 고치기를 둘 다** 같은 항목으로 돈다.
- 한쪽에만 걸린 조건(`isNew &&`, `!editing` 등)을 코드에서 찾아 서버 규칙과 대조한다. 서버가 고치기에서도 막는 규칙이면 화면도 막아야 한다.
- 고치기는 경우를 나눠 본다: 값을 안 바꾸고 저장 / 범위 안에서 바꿔 저장 / 범위 밖으로 바꾸기 / 옛 데이터를 그대로 저장.

## 8. 필수 값 하나씩 비우기 (묶음 값은 칸마다)

- 여러 칸이 한 묶음인 값(계좌 = 은행명·계좌번호·예금주, 주소 = 주소·상세, 일시 = 날짜·시간)은 **칸마다 하나씩 비워서** 각각 막히는지, 문구와 포커스가 맞는지 본다. 공백만 넣기, 형식 틀리기도 해 본다.
- 이 묶음을 판정하는 곳(저장 검사·안내 팝업 조건·서버)이 **모두 같은 칸을 보는지** 코드에서 확인한다.

## 9. 화면 크기별 글자·UI 깨짐 (자동 검사 + 캡처)

- 폭 **320 · 360 · 375 · 390 · 768 · 1024 · 1280 · 1440** 모두에서 바뀐 화면을 연다.
- 각 폭에서 이 스킬 폴더의 `text-layout-check.js` 에 있는 `TEXT_LAYOUT_CHECK(영역 선택자)` 를 `page.evaluate` 로 돌려 **빈 배열**이어야 통과다. 잡는 것: overflow(칸 밖으로 나감), clipped(의도 없는 잘림), orphan(마지막 줄 한두 글자), midword(어절 중간 줄바꿈), page(가로 스크롤).
- 자동 검사를 통과한 뒤에도 각 폭 캡처를 직접 열어 본다. 겹침·정렬·여백은 자동으로 못 잡는다.
- 검사기가 문제를 정말 잡는지 의심되면 같은 버그를 스타일로 일부러 넣어 한 번 잡히는지 본다.
- 긴 제목·큰 금액·긴 이름을 넣어 좁은 폭에서 겹치거나 깨지지 않는지 본다.

## 10. UI 검수 — 버튼·글자·여백을 기준 화면과 숫자로 비교

눈대중으로 "비슷하다"고 넘기지 않는다. 같은 종류의 기존 화면(기준 화면)을 하나 정하고, `getBoundingClientRect`·`getComputedStyle` 로 잰 값을 **기준 화면 값 / 새 화면 값** 으로 나란히 적어 비교한다. 프로젝트에 UI 가이드가 있으면 그 수치가 기준이다.

이 스킬 폴더의 `ui-audit.js` 에 있는 `UI_AUDIT()` 를 PC·모바일 폭에서 각각 돌리면 아래 항목 대부분을 한 번에 잰다(버튼 꺾임·44px 미만·잘림·겹침·가운데 어긋남, 12px 미만 글자, 16px 미만 입력 칸, 이웃 행·칸 겹침, 배지 겹침, 글자 크기 분포). 측정 결과는 그대로 믿지 않는다.

- 건수가 나온 항목은 **캡처로 다시 확인**한다. 잘려서 안 보이는 부분이 겹친 것처럼 잡히는 오탐이 있다. 겹침은 화면에 실제로 보이는 영역 기준으로 판단한다.
- 0건이어도 캡처를 본다. 측정이 못 잡고 캡처에서만 보이는 깨짐이 있다(예: 좁은 폭에서 제목이 한 글자씩 여러 줄로 꺾임).

**버튼**

- 깨짐: 버튼 글자가 두 줄로 꺾이거나 잘리지 않는지, 버튼이 칸 밖으로 나가거나 옆 요소와 겹치지 않는지 9장의 모든 폭에서 본다. 가장 긴 문구와 가장 좁은 폭을 함께 넣어 본다.
- 위치: 주 버튼의 자리(하단 고정 바, 오른쪽 정렬 등)가 기준 화면과 같은지 좌표로 비교한다. 하단 고정 버튼이 본문 마지막 내용을 가리지 않는지, 스크롤·키보드가 올라온 상태·기기 하단 안전 영역에서도 제자리에 있는지 본다.
- 크기: 같은 역할 버튼의 높이·폭·모서리 둥글기·글자 크기가 화면마다 같은지 비교한다. 누르는 영역은 폰에서 가로세로 44px 이상이어야 한다.
- 정렬: 버튼 안 글자·아이콘이 가운데에 있는지(중심 차이 0.5px 이하), 좌우 안쪽 여백이 대칭인지, 같은 줄 요소와 세로 가운데가 맞는지 본다.
- 상태: 기본·눌림·비활성·처리 중 모양을 각각 캡처한다. 처리 중에 버튼 폭이 바뀌어 옆 요소가 밀리지 않는지 본다.

**글자**

- 크기: 같은 역할(화면 제목·섹션 제목·본문·보조 설명·캡션·버튼 문구)의 글자 크기·굵기·줄 높이·색이 기준 화면과 같은지 비교한다. 새 화면에서만 쓰는 크기가 생기면 이유를 적는다.
- 위계: 제목 > 본문 > 보조 순서가 뒤집히지 않는지, 강조가 한 화면에 여러 개 겹치지 않는지 본다.
- 최소 크기: 폰에서 읽기 어려운 작은 글자(12px 미만)가 없는지 본다. 폰 입력 칸 글자가 16px 미만이면 iOS 에서 누를 때 화면이 확대되므로 16px 이상으로 둔다.
- 폭별 변화: PC 와 폰에서 글자 크기가 의도대로 바뀌는지, 중간 폭(768·1024)에서 어색하게 크거나 작지 않은지 캡처로 본다.

**표(테이블)·목록 행**

- 행·칸 겹침은 **모든 행**에서 확인한다. 첫 몇 행만 보지 말고 끝까지 스크롤하고, 가로 스크롤이 있으면 오른쪽 끝 열까지 본다.
- 눈으로만 보지 않고 잰다: 각 행과 칸의 `getBoundingClientRect` 로 위아래 행(위 행 bottom > 아래 행 top), 좌우 칸(왼쪽 칸 right > 오른쪽 칸 left), 칸 안 내용과 칸 경계가 겹치는 쌍을 전부 뽑아 **0건**이어야 한다.
- 겹치기 쉬운 경우를 일부러 만든다: 긴 글이 줄바꿈된 행, 빈 값만 있는 행, 배지·버튼·메뉴가 여러 개 든 칸, 펼친 행(하위 행·상세), 선택·호버 상태, 합쳐진 칸.
- 고정 머리줄·고정 열은 스크롤하는 동안 아래 행과 겹칠 때 내용이 비쳐 보이거나 테두리가 끊기지 않는지 본다.
- 행 안에서 열리는 메뉴·툴팁·날짜 창이 다음 행이나 표 밖 요소에 가려지지 않는지 본다.
- 좁은 폭에서는 표가 가로 스크롤이나 카드 형태로 바뀌는지, 그 상태에서도 위 항목이 지켜지는지 본다.

**여백·정렬**

- 본문이 기준 화면과 같은 선에서 시작하는지 left 값을 비교한다(폰 좌우 여백, PC 본문과 헤더 정렬).
- 같은 종류 요소 사이 간격이 일정한지, 카드 안 카드처럼 틀이 겹쳐 여백이 두 번 들어가지 않았는지 본다.
- 버튼·이미지 주변은 확대 캡처로 다시 본다.

보고에는 잰 값 표와 기준 화면과 다른 항목을 적는다.

## 11. 가로 넘김·페이지 나눔의 마지막 페이지

- 가로로 넘기는 목록은 **첫 페이지만 보지 말고 끝까지 넘겨** 카드 수가 적은 마지막 페이지를 캡처한다. 카드가 다른 페이지 높이만큼 늘어나거나 줄어드는지 카드 높이를 숫자로 비교한다.
- 같은 이유로 일반 목록도 첫 화면만이 아니라 끝(마지막 페이지, 무한 스크롤 끝)까지 본다.

## 12. 상태별 화면

- 느린 응답(API 를 일부러 늦춤), 빈 결과, 오류·재시도 상태를 각각 열어 본다. 로딩 표시가 화면 가운데에 머무는지, 무한 로딩 대신 오류 안내가 나오는지 본다.
- 가능·불가 두 상태를 모두 본다. 할 수 없는 상태면 버튼을 활성으로 두지 말고 이유를 보여 준다.
- 외부 위젯·결제 창·모달이 떠 있는 상태에서 오류를 일부러 내 본다. 오류 안내가 그 뒤에 숨으면 안 된다.

## 13. 자주 놓치는 것

- **시안 대신 실제 화면**: 판단용으로는 흉내 낸 시안이 아니라 실제 앱 화면 캡처를 보여 준다.
- **이미지 여백·모서리**: 이미지 모서리와 컨테이너 모서리가 일치하는지, 남는 여백이 없는지 확대 캡처로 확인한다.
- **요구 개수·요구 버튼**: 요청받은 항목 수와 버튼을 화면에서 하나씩 세어 본다.
- **기존 정책 회귀**: 데이터 삭제·보존이 걸린 변경은 기존 정책(README·규칙 문서)부터 확인한다.
- **데이터를 바꾸는 동작**: 승인·결제·탈퇴처럼 되돌리기 어려운 동작은 화면 확인만을 위해 실행하지 않는다.

## 13-1. 폰 키보드가 뜨는 입력 — 3환경 × 11항목 (2026-10-04 실기기 지적 다수)

키보드가 뜨는 입력(댓글 시트·채팅·폼)을 만들거나 고쳤으면 아래를 **전부** 돈다. 한 항목만 보고 "확인 완료" 금지. 고칠 때마다 전체를 다시 돈다.

**환경** (iOS 시뮬레이터 — 내장 브라우저로는 키보드를 못 띄운다)
- A. **지금 스토어에 깔린 앱과 같은 조건**: 키보드 플러그인 없이 빌드한 시뮬레이터 앱(웹뷰가 키보드만큼 줄어드는 방식). 웹 배포는 이 앱에 바로 나가므로 가장 중요.
- B. 새 버전 앱(키보드 플러그인 있음).
- C. 시뮬레이터 사파리.
- 시뮬레이터 메뉴 I/O > Keyboard > Connect Hardware Keyboard 를 꺼야 화면 키보드가 뜬다.

**항목** — 캡처, 움직임은 `xcrun simctl io booted recordVideo` 녹화를 초당 60장으로 잘라 본다.
1. 입력칸 직접 눌러 열기 → 입력 창이 키보드에 딱 붙음(틈·겹침 없음), 머리줄 제자리
2. 코드로 열기(답글 달기·수정·말풍선) → 1과 같음(두 배로 떠서 화면 위에 붙지 않음)
3. 키보드 뜬 채 뒤 글 위아래로 끌기 → 글만 움직이고 머리줄·입력 창·키보드 고정, 깜박임 없음
4. 키보드 뜬 채 앱 나갔다 오기 → 입력 창이 키보드 뒤로 숨지 않음
5. 키보드 올라오고 내려가는 순간 → 입력 창이 늦게 따라오거나 사이로 본문이 비치지 않음
6. 등록·저장·취소 뒤 → 키보드 내려가고 접힘, 하단 탭·스크롤 위치 원래대로
7. 바깥 눌러 키보드 내리기 → 접힘, 쓰던 글 남음
8. 한글 조합 입력 → 글자 깨짐·사라짐 없음
9. 하드웨어 키보드 연결 상태 → 입력 창이 엉뚱한 곳에 뜨지 않음
10. 작은 화면(320×568)·큰 화면 → 화면 밖으로 넘치지 않음
11. 입력 중 입력칸 주변 모양이 바뀜(보내기 뒤 안내 줄·버튼 줄이 생기거나 사라짐, 위 카드가 화면 밖으로 나감) → 깜박이는 커서가 입력칸 안에 있음, 보낸 메시지가 입력 창 뒤로 가려지지 않음. 아이폰 WebKit 은 포커스된 칸이 레이아웃으로 움직이거나 위·옆 요소가 바뀌어도 커서를 다시 그리지 않는다(스크롤·입력 때만) — 입력 중엔 입력 창 안 줄을 넣고 빼지 말고, 꼭 바꾸면 크기 변화(ResizeObserver)를 보고 `setSelectionRange` 재지정·스크롤 1px 움직였다 되돌리기로 다시 그린다. 첫 열기(키보드 높이 어림값 ≠ 실제)도 같은 원인이라 함께 본다. 운영 화면과 같은 조작으로 나란히 비교(2026-10-08 대화방 — 보낸 뒤 커서가 [수락] 버튼 위에 남음)

결과는 환경 × 항목 표로 보고한다(통과/실패/못 봄 — 못 본 칸은 이유).

## 15. 화면 테스트 뒤 로컬 로그 확인 (화면이 멀쩡해 보여도 필수)

화면 클릭·캡처 확인이 끝나면 **그 테스트 동안 쌓인 로그를 전부 열어 이상이 없는지 확인한 뒤에** 완료로 보고한다. 화면은 정상인데 뒤에서 오류가 나는 경우(조용히 삼킨 예외, 빈 목록으로 대체된 500, 실패한 부가 요청)를 여기서 잡는다.

- **테스트 시작 시각을 적어 두고 그 뒤 로그만 본다.** 다른 작업의 로그와 섞어 판단하지 않는다.
- **브라우저 콘솔**: `error`·`warn` 전부. 프레임워크 경고, 잡히지 않은 Promise 거부, 조각(chunk) 로드 실패, 이미지 404.
- **브라우저 네트워크**: 4xx·5xx·실패 요청. 의도한 401·404 인지 요청별로 구분하고, 같은 요청이 반복 호출되는지 본다.
- **서버 로그(테스트에 쓴 서버 전부)**: `ERROR`·`WARN`·예외·스택 트레이스. 동작 한 번에 같은 쿼리가 줄줄이 나가는지(N+1), 느린 쿼리, 외부 연동 실패 로그.
- **화면 개발 서버 터미널**: 컴파일·타입 오류, 새로 고침(HMR) 실패, 누락된 import 경고.
- **판정**: 이번 변경과 무관해 보이는 오류도 "원래 있던 것"이라고 넘기지 말고 원인을 한 줄로 적는다. 이번 변경 탓이면 고치고 다시 테스트하고, 기존 문제면 보고에 따로 적는다.
- **보고**: 완료 보고에 "콘솔·네트워크·서버 로그 확인 — 이상 없음" 또는 발견한 항목을 적는다. 확인하지 못한 로그가 있으면 못 봤다고 적는다.

## 16. 내장 브라우저로 돌릴 때 요령

- PC 폭(1280~1440)이 브라우저 창보다 넓으면 캡처에 화면 왼쪽 일부만 찍힌다. 오른쪽 끝(펼침 버튼, 오른쪽 정렬 버튼)이 캡처에 들어왔는지 확인하고, 빠졌으면 화면을 축소해 전체를 한 장으로 찍거나 구역을 나눠 찍는다.
- 폭 8개 반복(9장)은 같은 주소를 폭별 iframe 으로 열어 그 안에서 검사기를 돌리면 한 번에 끝난다. 오래 걸리면 백그라운드로 돌리고 결과만 나중에 읽는다.
- 개발 서버가 띄우는 표시(프레임워크 개발 도구 버튼 등)가 화면을 가린 것은 앱 버그가 아니다. 구분해서 적는다.
- 포트가 다른 프로젝트와 겹치면 빈 포트로 띄우고, 테스트가 끝나면 띄운 서버를 내린다.
